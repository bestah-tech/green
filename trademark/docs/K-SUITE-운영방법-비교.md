# K-SUITE 운영 방법 정밀 정리 & 상표 이식 매핑

KSUITE2.0.0 코드(187파일)의 **실제 프롬프트·오케스트레이션**을 근거로,
특허심사가 "어떤 방법으로" 자동화됐는지 단계별로 뜯고, 그 각 기법이 상표에서
**되는지·안 되는지·조건부인지**를 매핑한다. `설계철학.md`의 결론(판단 주변만 자동화)을
코드 근거로 뒷받침하는 문서다.

---

## 1. K-SUITE 전체 구조 (모듈 × 게이트)

| 모듈 | 역할 | 핵심 산출물 |
|---|---|---|
| **suite/** | 공통 계층: 팝업·설정·케이스 저장·모듈 레지스트리·LLM 정책·런타임 라우터 | 승인 게이트·버전 체인 |
| **k-larc** | 발명 분석·리뷰 허브 (핵심 엔진) | 구성대비표·의견서 초안·리뷰 점수 |
| **k-query** | 검색식 생성 — 3레이어 | boolean 검색식 |
| **k-research** | 검색 에이전트 — 자동 반복 루프 | 인용문헌 후보·평가 |
| **k-scan** | 화면 캡처 분석 | 청구항 중심 유사성 스캔 |
| **k-notice** | 통지서 + HWPX 출력 | 의견제출통지서 |

전 모듈이 공유하는 원칙: **근거 제한**(제공된 텍스트만 사용, 창작 금지) + **JSON 강제** + **승인 게이트**(단계별 버전 고정).

## 2. K-LARC 핵심 파이프라인 — 특허 자동화의 정수

K-LARC이 하는 일은 "진보성/신규성 판단"이라는 열린 법적 질문을
**"청구항을 구성요소로 쪼개고, 각 요소가 인용문헌에 있는지 근거로 대조하는"**
닫힌·분해된·검증가능한 매칭 문제로 바꾸는 것이다. 실제 단계(프롬프트 실측):

### Step A — 구성요소 분해 (`step_a_features`)
- **LLM이 하는 판단**: 청구항 문언을 인용문헌과 대조 가능한 최소 기술요소(Feature)로 분해.
- **하드 제약**: "입력된 청구항 문언만 사용. 명세서·도면·기술상식·업계관행 등 **청구항 외부 정보 사용 금지**. 청구항에 없는 구성·관계·목적·효과 추가 금지."
- → 판단의 입력을 **닫힌 텍스트**로 못박는다.

### Step B — 근거 추출 (`step_b_rag`)
- **LLM이 하는 판단**: 각 Feature마다 "검색된 RAG 문맥에 의해 **직접 뒷받침되는** 근거"만 추출. MatchType = Explicit(직접 개시) / Equivalent(문구는 달라도 같은 기술적 역할).
- **하드 제약**: "검색된 문맥이 없으면 근거를 추정하지 말고 빈 배열. 사실·위치·인용문을 지어내지 마라. 확신 부족하면 출력하지 마라."
- **판단 원칙(명시)**: "표면 명칭이 달라도 ①핵심 기능 대응 ②입력/출력/위치 중 하나 이상 대응 ③문헌과 모순 없음 → 실질적 동일 검토. 단 목적·효과만 유사하면 대응 불인정."

### Step C — 다중 판정 (`step_c_multijudge`)
- **LLM이 하는 판단**: Judge Profile(판단 성향)에 따라 근거 채택(P/F)과 Feature 상태 판정: **ENTAIL**(근거 명확) / **PARTIAL**(일부·해석여지) / **NOT_FOUND**(근거 없음).
- **핵심**: 여러 Judge를 **서로 다른 성향으로** 돌린다 → 판단이 갈릴 수 있음을 인정하고 프로파일로 관리. 단 최종 결론은 도구가 아니라 심사관.

### Step D — 재탐색 (`step_d_repair`)
- 누락/부분일치 Feature에 대해 대체 쿼리 2~4개 생성 → 추가 근거 재검색. (K-Research 루프와 연결)

### Verification — 자기검증 (`verification`)
- **LLM이 하는 판단**: 1차 분석의 각 근거(EvidenceId)를 **원문 추출(source_snippets)과 대조**해 문제 항목만 출력.
- **결정적 장치**: Position을 숫자 센티넬(`⟪0012⟫`)로 못박아, LLM이 인용한 위치가 **원문에 실제로 있는지** 기계적으로 검증. 없으면 warning.
- → LLM의 출력을 **원문에 재접지(re-grounding)** 하는 안전망.

### 의견서 리뷰 (`opinion_notice_review`)
- 작성된 의견제출통지서가 "기술적·법적으로 정합한지" 0~100 점수 + 체크리스트(primary_doc / combination / support_gap / citation_grounding)로 평가. **결론이 아니라 초안의 방어가능성 점검.**

**→ K-LARC의 최종 산출물은 구성대비표 + 의견서 초안 + 리뷰 점수이지, "진보성 있음/없음"이라는 법적 결론이 아니다.** 현장 직관("정리해준 정도")은 맞되, 실제로는 근거접지 매칭까지 한다 — 다만 최종 확신은 심사관 몫으로 남긴다.

## 3. 검색 쪽 — k-query(생성) + k-research(반복 루프)

- **k-query 3레이어**: layer1(핵심 구성 추출·우선순위·관계) → layer2(확장·문맥필터·평가) → **layer3(boolean 검색식 조립·검증, `&` 조합)**. 조립·검증은 코드 성격.
- **k-research 자동 루프**: `query_seed`(초기 검색식) → 검색 실행(CDP로 KOMPASS 조종) → `citation_eval_json`(문헌 1건씩 feature별 exact/equivalent/partial/absent/conflict 판정 + 검색식 오탐 진단) → **`corpus_decision`(전체 결과를 한꺼번에 읽고** 다음 방향 결정: single_near_hit / pair_candidate_region / gap_feature_missing / noise_cluster / restart) → `query_refine`(검색식 보정) → 반복.
- **핵심 통찰**: `corpus_decision`은 결과를 **개별이 아니라 전체로** 보고 "다음에 뭘 할지"를 정한다 — 이게 곧 **triage(선별) 사고**다.

---

## 4. 왜 이 방법이 특허에서 "통하는가" — 네 가지 성질

특허 유사 판단은 아래 넷을 다 갖춰서 자동화 스캐폴딩이 성립한다:

1. **분해 가능**: 청구항 → 독립적으로 대조 가능한 Feature 단위.
2. **근거 접지(닫힌 세계)**: 판단 재료가 제공된 청구항 + 검색된 문헌 텍스트 안에 있다. 외부 지식 금지.
3. **검증 가능**: "이 Feature가 이 문헌에 있는가"는 원문 위치로 **체크 가능**. Verification 단계가 이걸 기계적으로 확인.
4. **기준 상대적 안정**: "같은 기술적 역할" 표준은 Judge 간 대체로 수렴. (다중판정은 잔차 관리용)

## 5. 상표 이식 매핑 — 무엇이 되고 무엇이 안 되는가

K-SUITE의 각 기법을 상표에 대보면 이렇게 갈린다:

| K-SUITE 기법 | 상표 이식 | 판정 | 이유 |
|---|---|---|---|
| Step A 구성 분해 | 표장 → 칭호·외관·관념·지정상품 분해 | ✅ **됨** | 이미 모듈 1에서 함 |
| Step B 근거 접지(창작 금지) | 관념·사용실태를 **제공된 텍스트 안에서만** | 🔶 **조건부** | 재료(사전·검색결과)를 넣어줘야 함. 인터넷 차단이 관문 |
| Step C 상태 판정(ENTAIL/NOT_FOUND) | 칭호/외관/관념 요소별 유사도 | 🔶 **부분** | 요소별 후보 판정은 되나, **최종 유사/비유사는 접지된 정답이 없음**(재량) |
| Verification 원문 재접지 | 인용 판례·문구가 등록 자산에 실재하는지 | ✅ **됨** | 이미 근거 제한으로 포팅. 문구 자산 검증 |
| 다중 Judge 프로파일 | 심사관 재량 성향 반영 | 🔶 **변형 이식** | 판례가 갈리는 건 정상 → "정답 수렴"이 아니라 **심사관 본인 기준(교정지시) 적용**으로 |
| k-query 검색식 생성·검증 | 정교 검색식 10종 + 개수·기호 검증 | ✅ **됨** | 이미 모듈 2에 이식(코드 검증까지) |
| k-research 자동 루프 | 검색식 자동 입력·실행·수집 반복 | 🔶 **진행중** | 결과 읽기는 됨. 입력폼 구조 확보 후 가능 |
| **corpus_decision 전체 선별** | **후보 20개 triage → 핵심 3~4개** | ✅ **됨(핵심 기회)** | 유사도·유사군겹침·다수공존으로 정렬. 모듈 4 방향 |
| k-scan 청구항중심 스캔 | 표장중심 스캔 | 🔶 **부분** | 외관(이미지) 비교는 LLM 이미지 입력으로 일부 |
| k-notice 통지서·HWPX | 통지서·HWPX | ✅ **됨** | 이미 모듈 5에 이식 |

### 결정적으로 "안 되는" 두 가지 (특허엔 없는 상표 고유의 벽)
1. **최종 유사판단의 자동 확정** — 특허의 "이 Feature가 문헌에 있는가"는 원문으로 체크되지만,
   상표의 "퓨리젠 ≈ 퓨리진?"은 **접지할 정답 텍스트가 없다.** 법이 재량으로 남긴 영역이라
   Verification 같은 재접지가 원천적으로 불가능. → 심사관이 반드시 결론.
2. **관념·사용실태·저명성의 근거 접지** — 특허는 닫힌 문헌 DB로 접지되지만,
   상표의 이 축들은 **열린 인터넷**(사전·거래실태)에 있고 회사망에서 차단됨.
   → 인터넷 열리면 접지 가능, 막히면 "심사관 검색→붙여넣기→도구 구조화"의 반자동.

## 6. 명확해진 결론

- **특허가 자동화가 잘 되는 이유**: 판단을 *분해→근거접지→검증→선별*의 스캐폴딩에 태울 수 있고,
  각 단계의 답이 제공된 텍스트로 **체크 가능**하기 때문. K-LARC은 그 스캐폴딩의 정석이다.
- **상표에서 할 수 있는 최대치**: K-LARC 스캐폴딩의 **거의 전부**(분해·근거접지·구조화 대비표·인용 검증·다건 선별·문구 초안)를 이식할 수 있다. 실제로 대부분 이미 이식했다.
- **상표에서 원천적으로 안 되는 것**: (1) 최종 유사판단의 자동 확정, (2) 관념·실태·저명성의 인터넷 접지.
  (1)은 이식하면 **안 되는** 것(재량 침해), (2)는 못 하는 것(망 정책).
- **따라서 방향**: corpus_decision식 **triage + 후보별 근거접지 브리핑**(모듈 4)이 가장 큰 임팩트.
  이건 K-LARC이 특허에서 한 일을 상표에서 정확히 재현하는 것이며, 최종 확신만 심사관에게 남긴다.
